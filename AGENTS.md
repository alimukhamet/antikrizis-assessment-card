# Project ownership

The owner asked Codex to act as project manager and technical owner on 23 September 2026. Own triage, priorities, implementation, regression prevention and release verification. Do not make the owner diagnose technical failures or coordinate routine follow-ups.

- Read the ownership rules and open issue register in `RELIABILITY.md` before starting issue work. Preserve confirmed business rules in `README.md`.
- A deal ID is enough to begin: inspect its saved feedback, current state, application version, draft revision and existing operation receipts. Ask for missing evidence only after using the available evidence.
- Fix the cause and verify the employee's affected workflow. Preserve answers, originals, confirmations and uncertain write receipts. Never invent client facts or bypass a business gate to make a test pass.
- Distinguish implemented, locally tested, deployed and verified live. A preview download, a passing readiness check or green CI alone does not close a final submission or lawyer-handoff issue.
- Keep an issue open when the newest reported failure has not been reproduced. Record the evidence, scope of a workaround and exact remaining verification step.
- For a release, use the existing canonical GitHub workflow and preserve concurrent changes. Test old open tabs, reload and saved-state recovery when relevant to the change.
- Update the register as evidence changes. Give the owner a concise result, remaining blocker and next action. Do not claim ongoing background work unless an actual automation is configured.

These rules supplement the user's model, authorization and business instructions; they do not expand permission to submit real contracts, change client facts, transmit credentials or create recurring jobs.
