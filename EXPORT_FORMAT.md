# Assessment evidence export

The authenticated `/api/assessment/:dealId/export` route emits UTF-8 NDJSON. Export format version 2 preserves insertion order and captures the database rows in one D1 batch transaction. This exports one assessment; it is not a full production backup or a completed migration.

Require the first `manifest` and final `complete` record. Reject missing, duplicate or mismatched records/counts. The included questionnaire definition has its own schema version. Originals remain authenticated download paths, not embedded files. Download every original while source access is available and verify its byte size and SHA-256 before retiring the source. Extraction results are included; stored hashes refer to the original JSON encoding in object storage, not arbitrary destination re-serialization.

Version 2 adds `sequence` to reviews, submissions and upload manifests. It is the original SQLite insertion sequence, scoped to each record type. Preserve it on import. Do not order tied timestamps by UUID or compare sequence numbers across types. Replay reviews in ascending sequence, including `unresolved` records that withdraw earlier confirmations. Only reviews matching the current identity revision and intended extraction may supply answers. Version 1 cannot establish the order of tied timestamps; recover that order from the source database.

Keep original entity IDs, identity revisions, actor/authentication provenance, hashes, payloads and idempotency keys. External CRM references belong to adapter mappings; migration must not rewrite historical evidence or imply renewed verification. Source R2 keys are storage locators and may map to new locations after integrity checks.

Never replay external side effects automatically during import. Pending, writing or uncertain submission/upload/history receipts require readback against their original external destination. Migration must not turn uncertainty into a new upload or comment. Preserve the pinned contract renderer archive associated with saved submissions.

Before switching production, restore into isolated storage and compare original hashes, extraction versions, review decisions (including withdrawals), draft revisions and receipt states. Verify authenticated worker flows. Retain source data, publication version and object storage for rollback. This format alone does not establish a tested rollback.

Run `node scripts/validate-assessment-export.mjs /absolute/path/export.ndjson` before importing. This offline check rejects incomplete streams, unsupported versions, duplicate records, mismatched counts, wrong-case records, broken document/extraction references and reordered histories. It does not modify the export or contact Bitrix. A successful result is structural verification only: original file bytes, contract renderer archives and an actual destination restore still require separate verification.

For original-file verification, save each authenticated original under `originals/<original_sha256>` (no extension), then run `node scripts/validate-assessment-export.mjs /absolute/path/export.ndjson --originals /absolute/path/originals`. The checker reads every referenced original, verifies its exact byte size and SHA-256, and rejects missing files, symbolic links and changed content. It uses a bounded streaming read rather than loading all PDFs into memory. Keep the export and originals private. This still does not verify document authenticity, contract renderer archives or a destination import, and it never replays external writes.

D1 transaction behavior: https://developers.cloudflare.com/d1/worker-api/d1-database/#batch

Credential handoff records use upload manifest `scope: credentials` and `eds:<sha256>` references rather than ordinary PDF document IDs. They preserve the user-approved legacy filename, which includes the sanitized password: treat the authenticated export as sensitive. Key bytes are sent directly to Bitrix and are not included in the evidence-original directory. `originalBytesVerified` covers only exported ordinary document originals, not credential keys. A CRM migration must separately recover and verify the credential files using their recorded external references.

An isolated offline destination can now be created with `node scripts/restore-assessment-export.mjs export.ndjson originals contract-renderers NEW-destination`. The destination must not exist. The importer applies the repository's migrations to a new SQLite database, preserves entity IDs and sequence row IDs, verifies original and extraction-result hashes, and copies each pinned contract renderer from the supplied trusted archive. It stores objects under hashed filenames plus an object-key mapping, writes a completion marker only after success, and removes its own incomplete destination on failure. Existing destinations are never overwritten. It neither imports credentials from Bitrix nor connects a running destination CRM; no external actions are replayed. Renderer bytes are copied from the trusted supplied archive; the tool does not independently attest their provenance. Credential recovery, a destination application adapter and hosted restore acceptance remain separate steps.

Verified credential manifests for the current identity now include `credentialDownloads` with authenticated download paths. The endpoint verifies case membership, current identity revision, the saved credential receipt and the returned byte hash/size before downloading. It uses a generic credential filename in response headers; the user-approved legacy filename remains in the protected manifest. Save these separately from ordinary originals and verify each advertised hash. Historical credentials from older identity revisions and unverified uploads are not exposed by this path and require separate operator review. The offline importer still reports credential originals as excluded until they are separately supplied and verified.

Supply an optional final `credential-originals` directory to the restore command to include credentials. Store each recovered key under its SHA-256 filename. Before creating the destination, the importer requires verified credential receipts and checks every key's exact size and hash. Keys are copied into a separate private `credentials` directory; the completion report states the checked count. Unverified credential histories prevent this complete-credential mode and require operator resolution. The default four-argument restore still excludes credential bytes.


## Worker mistake reports

`/api/tool-feedback?format=ndjson` exports append-only reports as `assessment-feedback-ndjson`, schema version 1. It is a separate export from client assessments. The first `manifest` gives export time and scope; each `feedback` includes the original report ID, request ID, server-attributed employee, deal ID when selected, step, optional question ID/label, message, client/server release versions and creation time. The last `complete` includes the report count. Reject a stream without both boundary records or with a mismatched count. Preserve report IDs and employee attribution when importing; do not create fresh reports by replaying the POST endpoint.

Ali can export all employees' reports. Other employees can export only their own, using the existing session identity. Descending insertion sequence excludes later arrivals during export; records are immutable. The UI automatically captures location only, without copying answer values, document bytes, passwords or credentials. Free-text messages are employee-provided and should still be treated as confidential.

Client answers remain keyed by the versioned questionnaire definition, with separate repeated loan/job/benefit rows, document hashes, field-source references, review history and final submission snapshots. Keep these raw records for future analysis; the rendered lawyer card is an output, not the only stored representation.
